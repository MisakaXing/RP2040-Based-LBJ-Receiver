# DMA/AFC 修复及提交前验证

日期：2026-10-04（北京时间）。普通版发布版本 5.11；W 版 5.13-W。

实机专项在递增版本号之前完成，设备测试时版本为 5.10 / 5.12-W。
本次发布仅在已验证执行代码上递增版本号，并更新测试和文档；没有再次刷写设备。

提交前自动回归：普通版固件 76 项、W 版固件 238 项通过；对应 PicoUpdater 测试 75 / 76 项通过。合计 465 次测试执行，两分支包含重复场景。测试需从固件目录运行，或设置 PYTHONPATH=rp2040-main-program。

## 修复范围

- 保留 512 个 32 位字的 DMA 环形缓冲、射频频率、PPM、带宽、增益及正常 CPU 频率。
- 连续直接模式的 AFC 不会自动为每个新突发重新计算。未同步时仅在无积压的新前导码上安全重捕获；连续采样但 15 秒没有同步时有界恢复。已同步负载不重启，寄存器查询最多每秒四次。
- 重新捕获按序停止 PIO/DMA、清 FIFO/移位状态、恢复 PIO 指令入口、重置 DMA，再请求带 PLL 重锁的接收重启。
- 只放行 PLL 已锁定但 ModeReady/RxReady 尚未就绪的特定 FSRx 状态，避免原工作模式检查反复重新配置；其他配置错误仍检查。
- BCH 纠错表改为 1024 个 uint32 的定长数组。实机重建旧字典约占 14048 字节，新数组数据区 4096 字节，另有少量对象开销；接收线程启动前 GC。
- 诊断附加 RAM 占用曾使普通版线程栈及历史索引分配失败；这不证明所有正常程序不同步都由内存问题引起。
- 同步已完成的 DMA、温度和低电量保护改动；W 版同时包含网页历史功能。
- PicoUpdater 在两种硬件配置中上传 DMA / 保护模块，并在 main.py 之前写入，保留对旧固件包的兼容。

## 实机结果

设备：普通版 e66368254f677426；W 版 018540bc4336e6b4。

| 15 分钟新增落盘历史 | 15 | 6 |

两板均移除临时测试程序并硬件复位，恢复正常主程序。部署时 main.py、lbj_receiver.py 与当时本地修复逐字节一致，其他核对文件与测试前备份一致。

## 验证边界

- 五轮启动是硬件复位，不是同时断开 USB 和电池的真正断电冷启动。
- 受控回放经过实际 PIO/DMA 和生产解码链路，但绕过空中射频；物理 AFC 恢复另有实际寄存器故障注入验证。
- W 网页并发实机检查使用 RAM HTTP socket 模型运行生产服务代码，不是手机经过热点的端到端测试；未切换 Mac 网络，设备 TCP 自连接超时不计入通过项。
- 现场仍有 BCH 不可纠正码字，15 分钟普通版 164、W 版 43；不能等同于精确丢包数，也不能宣称所有空中报文都收到。
- W 在部分短窗口无输入字，随后未重启或写射频寄存器就自然恢复至 572 字、1 次同步。只读检查发现 FSRx 等待前导码，DMA/PIO 正常、无积压；不据此证明两台板卡灵敏度相同或没有弱信号漏收。
- 没有已知总发送数的受控 RF 源，不给出绝对接收率。短测不替代数日老化。
